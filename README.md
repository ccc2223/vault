# Vault

A personal Markdown notes app with encrypted offline storage and end-to-end encrypted sync through a Cloudflare Worker to a private GitHub repository. One password unlocks the app on your own devices. This protocol supports a single owner; it has no collaborator invitations, public links, or Obsidian sync.

## Privacy and unlocking

- The browser encrypts note contents, names, folders, spaces, attachments and sync metadata before upload. The Worker and GitHub receive ciphertext, opaque identifiers and wrapped key bundles.
- Normal unlocking uses one password field. Passwords are 15–256 Unicode characters, including spaces, and are used exactly as entered. Use a unique password generated by a password manager: the public password wrapper permits offline guessing.
- AES-256-GCM authenticates every record. PBKDF2-SHA-256 uses 600,000 iterations and a random 16-byte salt for password wrapping. HKDF-SHA-256 derives separate keys for every object revision and purpose. Each encryption uses a fresh 12-byte nonce.
- The random master key and independent random cloud access secret are wrapped together. Only the access secret is sent to the Worker. The vault password, master key and recovery key never go to the Worker.
- Local IndexedDB stores encrypted notes, file bytes, history, key bundles and checkpoints. localStorage holds only preferences and public server/vault identifiers. Sessions and usable keys stay in memory and are discarded on lock.
- Reload starts locked. Inactivity locks the app after an hour, including time spent in a suspended tab. Web Locks allow one editor tab per browser profile. Locking hides the UI, saves pending ciphertext and cancels requests; late responses cannot restore the editor.
- After a device has saved its encrypted cache, its local password can unlock it offline. A new device needs a network connection and the current vault password.
- Remote images require an explicit **Load remote image** click. Loading reveals your IP and viewing time to that host, with no referrer. Permission resets when the image is redrawn or Vault locks.

The hosting origin still supplies the JavaScript that handles your keys. A compromised release, origin, extension or unlocked device can read notes. Encryption does not conceal object sizes, update timing, Git commit authors, repository membership or traffic. See [SECURITY.md](SECURITY.md) for the protocol and threat boundaries.

## Editor

- Markdown live preview and source mode; wikilinks, aliases, heading links, autocomplete and backlinks.
- Folders and separate spaces; search, tags, daily notes, templates and a command palette.
- Task checkboxes and an aggregated Tasks view; editable tables, highlighted code blocks and an outline.
- Pasted, dropped or selected images, an in-app attachment viewer, resizing and SVG sanitization. Images can be at most 20 MiB; notes at most 5 MiB.
- Encrypted offline PWA, local trash for 30 days and the last 20 versions per note. Trash and history stay on that device; they are not synced.

Shortcuts: Ctrl/Cmd+P commands · Alt+D today's note · Ctrl/Cmd+O switcher · Ctrl/Cmd+Shift+O spaces · Ctrl/Cmd+S sync · Ctrl/Cmd+E live preview/source · Ctrl/Cmd+Shift+F search · Alt+N new note.

Spaces and attachment paths are logical paths inside the encrypted manifest. They do not appear as readable folders or files in GitHub. Remove notes through Vault; deleting encrypted objects directly can make checkpoints unreadable.

## Deploy a development vault

This is a fresh development format. There is no legacy plaintext import or migration. Use an empty private notes repository with an initialized `main` branch. The public application repository and private ciphertext repository are separate.

1. Host the application repository on GitHub Pages or another static HTTPS host. All committed app assets, including `e2ee.js`, `cloud-sync.js`, `vendor/` and `sw.js`, must be published together. No build is needed for hosting.
2. Create a fine-grained GitHub token restricted to the private notes repository with **Contents: read and write**.
3. Install Node.js 22+ and Wrangler 4: `npm install --global wrangler@4`. Run `wrangler login` locally with your Cloudflare account.
4. Check `wrangler.jsonc`: set the Worker name, `vars.REPO`, `vars.BRANCH` and `vars.ALLOWED_ORIGIN`. Keep the `LOGIN_LIMITER` Durable Object binding and migration. `ALLOWED_ORIGIN` is the application origin, without `/vault/`.
5. If the Worker URL changes, update `SYNC_URL` in `app.js` and `connect-src` in `index.html`, then publish those app assets.
6. Store the repository token: `wrangler secret put GH_TOKEN`. An existing correctly scoped token may be retained.
7. Run `npm run provision -- --worker-url https://YOUR-WORKER.workers.dev --app-url https://YOUR-APP/vault/`. It generates independent random `SESSION_SECRET` and `SETUP_TOKEN` values, writes them through Wrangler stdin and deploys the Worker. It prints a private, single-use setup link. The command must run from this checkout with the authenticated Wrangler executable available.
8. Open that link on a trusted device. The URL fragment is removed immediately; it is not sent to the web server. Create and confirm the password, then save and re-enter the generated recovery key. Only after confirmation does Vault publish its initial encrypted checkpoint.
9. Open the app on another device and enter the same password. No Cloudflare dashboard password change is involved.

The script does not publish GitHub Pages or create the GitHub token. Those account operations require the owner. Keep the printed setup link private until initialization. The setup capability cannot modify an initialized vault, and the first head creation uses GitHub compare-and-swap to prevent two initializations. After confirming setup, remove the obsolete secret with `wrangler secret delete SETUP_TOKEN`. A previous `PASSWORD` secret is unused and should also be deleted. Never put secrets into app source or `wrangler.jsonc`.

| Setting | Type | Purpose |
| --- | --- | --- |
| `GH_TOKEN` | Secret | Token scoped to the private ciphertext repository |
| `SESSION_SECRET` | Required secret | Independent random session-signing secret, at least 32 characters |
| `SETUP_TOKEN` | Temporary secret | One-time initialization capability |
| `REPO` | Variable | Private repository in `owner/name` form |
| `BRANCH` | Variable | Ciphertext branch; defaults to `main` |
| `ALLOWED_ORIGIN` | Variable | Exact allowed application origin(s), comma separated |
| `SESSION_HOURS` | Optional variable | Session duration, default and maximum eight hours |

The Worker never accepts the vault password. Login uses a random 256-bit access secret and a signed, expiring session. Every authenticated request checks the current head's vault identity and key epoch. Rotating the vault keys immediately rejects prior sessions. Rotating `SESSION_SECRET` also signs out all devices.

The required Durable Object reserves at most 10 login attempts per IP per 15 minutes, atomically, before parsing the body. Public bootstrap requests have a separate budget with the same limit. There is no global lockout. Missing trusted IP information or unavailable protection returns 503. A 429 includes `Retry-After`. Devices sharing one public IP share a budget.

## Password changes and recovery

**Change password and keys** in Settings verifies the old local password and completes a sync. Save and confirm the newly generated recovery key. Vault generates a new master key, access secret and recovery key, and reencrypts every current cloud record. Before publishing the new head, it atomically reencrypts the device cache and a resumable rotation journal under the **new password**. A failed head update leaves a recoverable journal. Reopen this device with the new password to resume; keep its browser data until rotation finishes.

Other devices retain their old local caches and any drafts. Unlock each with its previous local password, then use Sync settings to reconnect with the current vault password. Reconnection reencrypts that cache and resumes encrypted sync without discarding drafts.

If the password is lost, use **Recover with recovery key** from a fresh browser profile. Enter the saved recovery key and a new password, then save and confirm a new recovery key. Recovery rotates all keys and sessions and restores synced records. This implementation deliberately requires a fresh profile when the current profile contains saved notes, preserving the old cache for any unsynced drafts. The recovery key does **not** unlock that device's separately password-encrypted unsynced cache. Never clear a device's browser data while it may contain unsynced edits.

Old offline caches and old Git history remain decryptable to anyone who already has their old keys. Rotation protects the new epoch; it cannot revoke previously copied plaintext or erase earlier Git objects. Keep recovery material offline in a secure location. Neither the server nor the developer can reset a lost password without the recovery key.

If locking cannot save the last edits, keep the tab open and click **Retry saving and lock**. The app hides notes and retains the last in-memory copy until persistence succeeds.

## Sync and conflicts

Objects have random IDs and immutable revisions. Uploads complete before a conditional update of `e2ee/head.json` publishes a checkpoint. Failed or concurrent writes leave the previous head valid; unreferenced uploaded objects are retained. Commits use generic messages.

Sync pulls before pushing, on opening, Ctrl/Cmd+S, shortly after edits and when returning to an unlocked tab. Unedited open notes update immediately. When both devices edit a note, Vault keeps the local text and creates a conflict copy of the remote text. A remote edit made after a local delete survives. Tombstones prevent stale devices from silently resurrecting deleted entries. Files upload before the notes that refer to them. A failed remote authentication, hash or record check keeps the local draft and does not apply a partial download batch.

Known devices reject checkpoints older than the last saved generation, conflicting heads at the same generation and manifests omitting known entries. A new device has no prior checkpoint, so it cannot independently detect a full server rollback. Repository readers see only ciphertext; use the app to view and edit notes. General file attachments, collaborator sharing, remote garbage collection and history rewriting are outside this release.

## Development and validation

```sh
npm ci
npm run vendor
npm run test:unit
npm install --global wrangler@4
npm run test:runtime
npx playwright install --with-deps chromium firefox webkit
npm run test:browser
VAULT_BROWSER=firefox npm run test:browser
VAULT_BROWSER=webkit npm run test:browser
```

CI runs the protocol tests, the production login handler with real SQLite Durable Objects in workerd, and browser regressions in Chromium, Firefox and WebKit. Only the Chromium CDP touch-injection test is engine-specific. Browser tests use real IndexedDB and Web Crypto and pass actual encrypted requests through the Worker against an in-memory GitHub transport. No real account secrets or notes are used. `CHROMIUM_PATH` can select a system Chromium executable.

Before deploying, require green CI and test initial setup, a second-device unlock, offline editing, key rotation and recovery against the actual Cloudflare binding and private repository. Local mocks and workerd cannot confirm account credentials, configured origins or GitHub's live service limits. The 20 MiB limit is a protocol limit; mobile memory and deployed Worker resource behavior still require that deployment check.

When app assets change, bump the service-worker cache version. It caches only the public shell. Vendored dependencies and licenses are committed under `vendor/`; `npm run vendor` rebuilds them from the lockfile.
